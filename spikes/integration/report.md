# 통합 보고서: 스파이크 코어 병합과 선행 리팩터링 (spike/integration)

질문(docs/integration-g1.md): S2·S3·S4·S5·S8의 코어 변경을 한 브랜치로 합치고, git이 잡지 못하는 의미 충돌 6건을 고쳐 G1에 넘길 수 있는가?

**결론: 합쳤고, 의미 충돌 6건을 시험으로 고정한 뒤 모두 고쳤다.** 재측정 수치는 이전 스파이크 보고와 같다(5절). 문서에 없던 상호작용 6건도 더 찾아 고쳤다(4절).

## 1. 무엇을 합쳤나

| 순서 | 브랜치 | 방법 | 텍스트 충돌 |
|---|---|---|---|
| 기반 | spike/s5-annotations (s3 포함) | `git worktree add -b spike/integration` | — |
| 1 | spike/s8-merge | `merge --no-ff` | `parity.py` 1(오류 사례 목록: 양쪽 유지) |
| 2 | spike/s4-families | `merge --no-ff` | `commands.py` 3, `engine.py` 2, `errors.py` 1, `ifc_model.py` 1, `parity.py` 1 |
| 3 | spike/s2-roundtrip | `merge --no-ff` | `commands.py` 2, `engine.py` 2, `ifc_model.py` 6, `parity.py` 1 |

S7·S9·S10은 코어를 고치지 않아 범위 밖이다. 충돌 해결의 요점은 다음과 같다.

- **commands.py**: 삭제의 관계 목록에 S5 `annot_of`와 S4 `of_type`를 둘 다 넣었다. S2의 `attach`와 `complex_material`을 `_delete_one`에 유지했다. `model.validate`는 S3의 뷰 레벨 검사와 S4의 패밀리 평가 오류를 둘 다 센다.
- **engine.py**: 신원 만들기에 S4의 `ifc_class` 인자, S3의 "비 IFC 요소는 신원 없음", S2의 `prune`을 모두 넣었다.
- **ifc_model.py**: 상태 필드를 한 `__init__`으로 합쳤다. `remove_identity`는 S3의 개구부 잃은 문 목록, S4의 패밀리 투영 해제, S2의 `_remove_product`를 한 흐름으로 합쳤다. 의미 덤프는 S2의 `make_norm`을 정본으로 삼고 S4의 `IfcTypeObject` 참조 접기를 거기에 넣었다.
- **parity.py**: 각 스파이크의 준비 단계(`_V1`, `_A1`, `_FAMILY_PRE`)와 오류 사례, 입력 파일 준비를 모두 유지했다.

병합 직후 비-slow 시험 중 S5 한 건만 실패했다(`commands.search`가 6,000B 상한에서 한 쪽에 안 들어감). 쪽을 넘겨 모아 대조하도록 고쳤다.

## 3. 리팩터링

1. **레지스트리(`kinds.py`, ADR-0013)**: ifcopenshell을 import하지 않는다. 요소 9종, 관계 6종, 효과 5종을 정의한다. 엔진·IFC 모델·질의·병합·가져오기·커맨드가 여기서 파생한다.
   - `succ`만 끝 요소가 지워져도 남는 것으로 표시했다. 한 번 쓴 id는 다시 만들 수 없다는 S5 규칙 때문이다.
2. **시작 상태 로그 기록**:
   - seq 0 항목은 리비전에 세지 않고 되돌리기 대상이 아니다.
   - 서로 다른 가져오기에서 갈라진 파일의 병합은 `CONSTRAINT`로 거절한다.
   - 접기가 가져온 IFC 값을 조상 시드로 넣어, 한쪽의 삭제가 사라지거나 수정 대 삭제 충돌을 놓치는 일을 막는다. 시드를 끄면 `test_1b`가 실패하는 것을 확인했다.
3. **저작 확인 단일 관문**:
   - `Ctx._frozen_check` 하나를 `authored()`, `put_el`, 새 관계, `set_material`이 같이 쓴다.
   - 관계는 맺을 때만 검사한다. 저작 문을 지울 때 분리된 호스트와의 관계를 끊어야 하기 때문이다.
4. **해시 형식 번호**:
   - `CLOSURE_FORMAT`은 "1"이 S2, "2"가 통합이다.
   - 열 때 번호가 다르면 원본 바이트로 재판정해 `projection_hash`를 갱신한다.
   - 저작→분리는 동결하고 시작 상태 기록도 고친다. 분리→저작으로는 되살리지 않는다.
5. **병합 확장**:
   - 요소 9종, 관계 6종, `att` 효과를 다룬다.
   - 새 의미 규칙: `REL_ENDS`, `VIEW_DELETED`, `TYPE_DELETED`, `TYPE_MISSING`, `VIEW_MISSING`, `FINST_INVALID`, `FINST_OUT_OF_HOST`, `VIEW_LEVEL_DELETED`, 뷰 이름 중복.
   - 병합이 지우는 가져온 요소의 외래 부속을 `att`로 먼저 남긴다.
6. **패리티·린트**:
   - 패리티 도구가 `commands.search`를 쪽 단위로 모은다.
   - ifcopenshell 직접 사용 금지 계약에 `merge`, `kinds`, `limits`, 패밀리 순수 모듈을 넣었다.
   - 허용 목록은 engine, ifc_model, foreign(외래 IFC를 읽는 가져오기 계획), family.ifcproj, family.validate(IFC4 스키마의 클래스 이름 확인)다.
7. **도면**: `is_drawn_wall`, `view_omitted`, `hosted_opening`을 더했다.

## 6. 확인하지 못한 것

- Revit 표본(비공개)은 환경변수가 없어 건너뛰었다(시험 5개).
- Claude 토크나이저로는 응답 크기를 재지 못했다(tiktoken 대용).
- 재측정 중 다른 프로세스가 동시에 돌아 시간 값은 부하의 영향을 받았다.

## 7. 한계

- 통합 전에 가져온 프로젝트에는 시작 상태 기록이 없다. 병합하려면 `ifc.import`로 다시 가져와야 하고, 병합이 `CONSTRAINT`로 알린다.
- ~~패밀리·뷰·주석은 가져오기에서 의도를 복원하지 않아 외래로 분류된다.~~ 패밀리는 10절에서, 뷰·치수·태그는 11절(ADR-0015)에서 복원한다.
- 병합의 패밀리 규칙은 개구부가 호스트 벽 안에 들어가는지와 평가 오류만 본다.
- 분리를 저작으로 되돌리는 경로는 없다.
- 단일 환경에서만 쟀다.
- 의미 충돌은 코드를 읽고 재현한 것이며, 모든 짝을 체계적으로 탐색한 것은 아니다.

검수 중 확인한 것(결함 아님): 같은 IFC라도 `guid`를 따로 정하지 않고 가져오면 `project_uuid`가 달라 병합이 거절된다(의도된 규칙). 되돌리기 거절(항목 4)은 재판정이 판정을 뒤집는 드문 경로에서만 나타난다.

수치(같은 한 대, 다른 프로세스와 겹쳐 돈 시간은 참고용): 코어 비-slow 369개(이전 345 + 검수 회귀 24) 중 364 통과, 5 건너뜀(Revit 환경변수 없음), 실패 0. 패리티 C 100%(불일치 0, 음성 대조가 불일치를 잡음). `commands.search`는 쪽마다 6,000B 이하(시험 통과). import-linter 5계약 유지. 검수 재현 스크립트 전부 재실행: 결함 재현 항목(`sc2`·`sc2b`·`sc4`·`sc5`·`sc6`·`sc7`·`sc12`·`legacy_flip`)은 모두 해소됐고, 회귀 점검 항목(`sc1` 되돌리기 끝까지 후 재오픈 해시, `sc3`, `sc9`, `sc10`, `sc11`, 병합 퍼즈 가져온 기반·저작 기반 각 25시드: INTERNAL·IO_ERROR 0, 열어 다시 계산한 해시 일치, undo 일치)는 이전과 같다. `sc8`(항목 7)은 당시 위의 한계대로 호스트 벽이 분리로 동결됐고, 10절의 조치 뒤에는 전부 authored 다.

## 10. 패밀리 의도 왕복 (ADR-0014)

질문: 패밀리 인스턴스가 있는 저작 프로젝트를 IFC 로 내보냈다 다시 가져와도 전부 authored 이고 해시 3종이 같은가? 외부에서 패밀리를 바꾸면 그 요소(와 영향받는 호스트)만 분리되는가?

**결론: 그렇다.** 가져오기가 패밀리 타입(`ftype`)과 인스턴스(`finst`)의 의도를 복원한다. 뷰·주석(S3·S5)은 IFC 에 담기지 않아 이 절 시점에는 복원하지 못했고 한계로 남겼다(11절이 닫는다).

### 10.1 원인과 조치

원인은 8절 항목 7 그대로다(인스턴스·타입의 `DoBIM_Intent` 를 해석하지 못해 인스턴스와 개구부가 외래, 호스트 벽의 `voids` 가 달라 호스트가 분리). **패밀리 정의는 IFC 에 이미 들어 있다**: 타입의 `DoBIM_Intent` 에 레시피 전문과 타입 값, 인스턴스의 것에 타입 id·호스트(또는 레벨)·값이 있다. 그래서 파일 형식은 바꾸지 않았고 `CLOSURE_FORMAT` 도 올리지 않았다(문·벽·레벨의 정규화는 그대로, 새 규칙은 새 종류에만 적용). 의도에는 별도 형식 번호가 없다(모양을 키 집합으로 엄격히 검사한다). 이 변경 전에 가져온 프로젝트는 열 때 다시 판정하지 않아 옛 판정 그대로 열린다.

## 11. 뷰·치수·태그 왕복 (ADR-0015)

질문: 뷰·치수·태그가 있는 저작 프로젝트를 IFC 로 내보냈다 다시 가져오면 전부 복원되고, 해시 3종이 같고, 복원된 뷰의 도면 산출이 같은가? 외부에서 정의를 건드리면 안전하게 떨어지는가?

**결론: 그렇다.** 정의를 프로젝트 속성셋에 싣고 가져올 때 검증해 되살린다. 형식·판정 규칙의 결정 이유는 ADR-0015 에 있다.

### 11.1 설계 결정 (ADR-0015 요약)

- **그릇: `IfcProject` 의 속성셋 `DoBIM_Defs`, 정의 하나 = 속성 하나(이름 = 요소 id, 값 = `IfcText` JSON `{kind, family_id, params, check}`).** 후보 (a) 요소마다 `IfcAnnotation`, (b) 속성 하나에 정의 묶음, (c) 속성 하나씩 중 (c)를 골랐다. (a)는 `IfcProduct` 를 늘려(형상 없는 개체가 다른 도구의 모델 트리에 뜬다. `IfcAnnotation` 은 주석 형상을 담는 클래스라 뷰와 뜻이 다르다) `ifcdiff`·M1~M8·요소 클로저 체계에 닿고, 그림이 파생이라 비교할 형상이 없는 것은 (a)에서도 같아 어차피 정의 자체에 변조 탐지가 필요하다. (b)는 정의 하나가 손상되면 전체를 못 믿고 하나를 고쳐도 전체를 다시 쓴다.
- **변조 탐지 `check` = sha256(id, kind, params).** 일부만 고친 변조(위치·참조·뷰 설정)를 잡는다. 인증이 아니다(정의 전체를 맞는 해시로 다시 쓴 위조는 통과하고, 모든 검증을 거친 뒤 커맨드로 만든 것과 같은 요소가 된다).
- **참조는 파일 안의 요소 판정이 끝난 뒤 따진다**: 저작 레벨·벽·문이면 복원, 파일에 없으면 고아로 복원(저작 상태에서 지운 뒤와 같다), 분리·외래·종류 불일치면 복원하지 않는다(낡은 값을 재게 된다). 정의가 속한 뷰가 복원되지 않으면 그 뷰의 주석도 복원하지 않는다.
- **복원하지 않은 정의는 파일에 그대로 남고 내보낼 때도 건드리지 않는다.** 소유 = 복원한 id + 새로 만든 id.
- **뷰·주석이 없는 프로젝트의 IFC 는 바이트까지 그대로**(속성셋을 만들지 않고, 마지막 정의를 지우면 속성셋도 지운다). `CLOSURE_FORMAT`·`.dobim` 스키마는 올리지 않았다(이유: ADR-0015 결정 7). 이 변경 전에 내보낸 IFC 는 정의 없이 열리고, 이 변경 전에 만든 프로젝트는 열어서 내보내면 정의가 실린다.
- 코드: `viewdefs.py`(순수: 정의 텍스트·검증), `ifc_model.py`(`sync_defs`·`adopt_defs`), `engine.py`(`_flush_defs`·소유 이어받기), `foreign.py`(`_read_defs`·`_restore_defs`).

### 11.5 한계·미확인

- `check` 는 변조 탐지이고 인증이 아니다. 정의를 올바른 해시와 함께 다시 쓴 위조(예: 치수 참조를 다른 저작 벽으로)는 모든 검증을 통과하면 복원된다. 요소 형상은 건드릴 수 없고 피해는 잘못된 도면이다.
- 복원하지 않은 정의의 id 와 같은 id 로 새 뷰를 만들면 그 속성을 덮어쓴다(복원하지 않은 정의는 요소가 아니라 id 충돌 검사에 안 걸린다).
- 다른 BIM 도구에서는 이 속성셋이 의미가 없다(보이지 않는다). 거기서 도면을 보려면 도면 내보내기(SVG·PDF)를 쓴다.
- 프로젝트가 정확히 하나가 아닌 IFC 에는 정의를 싣지도 읽지도 않는다.
- 정의 수만 개 이상은 재지 않았다(12,000개까지: 선형).
- 사람 판정이 필요한 기준(Revit 등 다른 도구가 이 파일을 열 때 경고가 없는지)은 이 PC 에 Revit 환경변수가 없어 **미확인**이다. `ifcopenshell` 의 검증기(express 규칙 포함)는 오류 0 이다.
