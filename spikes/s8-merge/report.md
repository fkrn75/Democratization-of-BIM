# S8 결과: 로그 기반 병합이 성립하는가?

판정: **합격(조건부)**. 기준은 "분기 2개의 커맨드 로그 병합 시나리오 10종에서 결정적 결과, 의미 충돌 감지"였다. 시나리오 23종(깨끗이 합쳐짐 8, 충돌 15)을 양방향으로 돌려 모두 만족했다. 독립 검수(조건부)에서 나온 결함은 모두 고쳤고 회귀 시험을 넣었다(아래 "검수 후 수정"). 대안("요소 차용만 지원")으로 후퇴할 필요는 없었다. 결론은 S1 모델(레벨·벽·문·조인·속성·재료)에 대한 것이다.

핵심: **커맨드를 다시 실행하는 rebase 식은 주 전략으로 부적합하고, 로그의 효과를 접어 만든 상태 델타의 3-way 병합 + 합친 결과의 재생성 검사가 성립한다.** rebase 식은 충돌 28회 중 16회를 조용히 성공시킨다.

## 병합 모델

- **단위(unit)**: 요소 존재·종류, 파라미터 필드 하나, 관계 하나, 속성 하나, 재료. 값은 정규 JSON이라 `1`/`1.0`/`true`가 구분된다. 로그 효과가 행 전체(`el: old_row -> new_row`)여도 이전·이후 행을 비교하면 필드 단위가 된다(architecture 11절 2항 충족).
- **공통 조상**: 두 `op_log`의 최장 공통 접두(seq·txn·행위자·op·인자·역효과가 같아야 함, 시각 제외). 트랜잭션 중간에서 끊기면 그 앞으로 물린다. **같은 상대를 앞서 병합한 기록이 있으면(취소되지 않은 `merge.apply` 항목의 `other_rev`와 합친 로그 접두의 지문 `other_fp`가 지금 로그와 맞으면) 3-way 기준을 그 접두 상태로 끌어올린다.** 조상 상태와 각 쪽 최종 상태는 효과를 접어 만든다. undo/redo도 로그 항목이라 따로 다루지 않는다(한쪽이 취소한 것은 순변화 없음으로 보인다).
- **3-way**: 단위마다 (조상, 우리, 상대). 한쪽만 바꿨으면 그 값, 같게 바꿨으면 그 값, 다르게 바꿨으면 충돌. 두 쪽을 바꿔 호출해도 결과가 같다(교환 법칙).
- **충돌 유형**
  - 단위 수준: SAME_FIELD, PSET_SAME_PROP, MATERIAL_SAME, DELETE_MODIFY, ID_COLLISION.
  - 합친 결과의 의미 충돌: HOST_DELETED, JOIN_TARGET_DELETED, DOOR_OUT_OF_HOST, DOOR_OVERLAP, DUPLICATE_WALL, LEVEL_NAME_DUPLICATE, DOOR_OUTSIDE_TRIMMED.
  - 그 밖의 규칙: LEVEL_DELETED, ORPHAN_UNIT, HOST_MISSING, LEVEL_MISSING, JOIN_DEGENERATE.
- **재생성 검사**: 합친 단위를 모델로 풀어 규칙을 검사하고, 조인 정리·문 상태는 `queries.py`의 실제 파생 질의(`wall_trim`, `door_status`)를 `RefGraph`로 다시 계산해 본다(architecture 11절 4단계). **병합이 새로 만든 위반만** 충돌이다. 우리 쪽이나 상대 쪽이 이미 가진 위반은 병합 탓이 아니다(s21).
- **해결은 명시적으로만**: `resolve=[{key, take: ours|theirs}]`(ID_COLLISION에만 `both`: 우리 요소는 그대로 두고 상대 요소를 결정적인 새 id로 옮겨 둘 다 살린다). 자동 해결은 없다. 충돌이 하나라도 남으면 합치지 않고 상태를 건드리지 않는다. 단위 충돌은 해당 쪽 값을 택하고(요소 충돌은 요소 전체), 의미 충돌은 반대쪽이 기여한 변경을 조상 값으로 되돌린다. 단위 충돌이 남아 있으면 의미 검사를 보류한다(보고가 방향에 기대는 것을 막기 위함). 해결 후 미리보기를 다시 읽으면 의미 충돌이 드러난다(연쇄).
- **기록과 되돌리기**: 병합은 `merge.apply` 로그 항목 하나이고, 효과는 우리 상태에서 병합 결과로 가는 차이다. `history.undo/redo`로 되돌려지며 로그 인자에 `other`, 실제 합친 `other_rev`, 그 접두의 지문 `other_fp`가 남는다.

## 무작위 병합 (`run_fuzz.py`)

S1 생성기(실패 입력·배치·undo 포함)로 조상 14항목 + 가지당 16항목을 120쌍 만들어 양방향 병합했다.

- 깨끗 45쌍은 전부 두 방향 해시가 같고, 되돌리면 병합 전 해시로 돌아간다.
- 충돌 75쌍은 전부 충돌 집합이 방향과 무관하고, 거부 시 상태가 불변이다. "미리보기 → 보이는 것 모두 해결 → 다시 미리보기"를 반복해 전부 합쳐졌고 IFC 일관·되돌리기가 성립했다.
- 불변식 위반 0, 내부 오류 0.
- 충돌 분포: DELETE_MODIFY 45, SAME_FIELD 26, LEVEL_DELETED 24, DOOR_OVERLAP 8, PSET_SAME_PROP 4, DOOR_OUTSIDE_TRIMMED 4, JOIN_TARGET_DELETED 3, HOST_DELETED 1, MATERIAL_SAME 1.

## 재실행(rebase 식) 대조

같은 시나리오에서 상대 가지의 취소되지 않은 트랜잭션을 우리 가지 위에 커맨드 그대로 재실행해 3-way와 비교했다(46회).

- 깨끗한 16회: 14회는 재실행 해시 = 3-way 해시, 2회(s16, 양쪽이 같은 변경)는 `CONSTRAINT`로 실패했다.
- 충돌인 30회: **16회는 조용히 성공**했다. 같은 필드는 마지막이 덮어쓰고, 중복 벽·겹친 문·조인 정리된 벽 밖의 문은 개별 커맨드가 유효해 통과한다. 13회는 방향에 따라 `NOT_FOUND`/`CONSTRAINT`로 실패했고, 1회는 재실행 불가였다. s12는 양방향 모두 조용히 성공하며 재생성 검사로만 잡힌다.

| 2 | 병합 뒤 자동 id 영구 충돌 | `Ctx.new_id`가 이미 있는 id·이번 실행이 이미 내준 id와 겹치면 n을 올려 다음 후보를 쓴다(결정적, 상태에만 의존). 충돌이 없으면 첫 후보 그대로라 S1 골든 해시·기존 id 불변(S1 시험 전부 통과). 양쪽이 같은 리비전에서 자동 id를 만든 s17은 `take: both`로 해결할 수 있다(위 모델, 상대 요소가 새 id로 이동, 되돌리기 가능, 재병합 멱등) |
| 3 | 배치에서 다른 변경 뒤·두 번째 `merge.apply`가 INTERNAL | 앞 커맨드가 상태를 바꿨다면(seq != head+1) USAGE로 거절. 병합이 첫 변경이면 뒤에 다른 커맨드가 와도 된다 |
| 4 | 같은 상대 재병합의 거짓 충돌 | `merge.apply`가 `other_rev`와 함께 합친 접두의 지문 `other_fp`를 기록하고, 다음 병합이 취소되지 않은 기록을 찾아 기준을 그 접두로 끌어올린다(상대가 우리를 합친 경우도 대칭). 취소한 병합은 쓰지 않아 다시 들여온다. 교차 병합(서로 합치고 갈라짐)은 한쪽이 후손이면 후손, 아니면 보수적으로 공통 접두로 되돌아간다. `merge.preview`에 `base`(`fork`/`prior_merge`)를 보고하고 `relation`은 이 기준으로 계산한다 |
| 5 | 상대 파일 내용 검증 부재, 조작된 효과가 커맨드 검증 우회(예약 pset `DoBIM_Intent` 통과) | 상대 로그를 읽을 때 열·seq 연속성·JSON·효과 모양·요소 행(종류·IFC 클래스·파라미터 이름·값 범위·이름 길이)·관계 종류·속성 이름/값(예약 pset·`id` 금지)·재료를 커맨드와 같은 규칙으로 검사해 위반이면 IO_ERROR. 상대 상태에 커맨드로는 못 만드는 구조 위반(레벨 없는 벽 등)이 있어도 IO_ERROR. 합친 결과도 같은 불변식으로 다시 검사(CONSTRAINT). 규칙이 `commands.py`와 같은지 시험이 대조한다. 모든 경우 상태 불변 |
| 6 | `mode=ro`로 열어도 상대 폴더에 `-wal`/`-shm` 사이드카가 남음 | 상대에 사이드카가 없으면(아무도 안 열고 있음) `immutable=1`로 열어 아무것도 만들지 않는다. 사이드카가 있으면(쓰는 중·비정상 종료) WAL을 읽어야 하므로 `mode=ro`로 열고, 우리가 새로 만든 사이드카만 닫은 뒤 지운다. 시험이 폴더 목록과 파일 크기·수정 시각까지 비교한다 |
| 7a | 같은 자리 벽 중복 판정 쌍 폭증(겹친 벽 1200개 580MB) | 묶음이 40개를 넘으면 쌍 대신 벽마다 하나씩 보고(선형). 작은 묶음은 쌍 그대로. 1200개가 20초 안에 처리되고 위반이 1200개다 |
| 7b | 상대가 속성을 지운 것을 수정으로 세서 거짓 DELETE_MODIFY | 값이 남는 변경만 수정으로 센다. 값을 쓰는 변경은 여전히 충돌 |

변이 시험에 트랜잭션 경계(M12), 반복 상한(M11), id 충돌(M13, M15), take 뒤바꿈(M16) 등 10종을 더했다.

## 발견과 권고

1. **자동 id는 같은 리비전의 두 가지에서 같은 값이 나온다**(`uuid5(프로젝트, kind:seq:n)`). 병합 뒤 충돌은 탐색으로 막았지만 s17 같은 동시 생성은 ID_COLLISION이다. `take: both`는 상대 요소를 새 id로 옮겨 살린다. 이때 새 id는 (프로젝트, 원래 id, 상대가 만든 seq)의 해시라 **방향(A←B와 B←A)에 따라 결과 id가 다르다**(내용은 같다). 방향 무관한 id가 필요하면 id 생성에 행위자나 가지 식별자를 넣어야 하고, 그러면 골든 해시가 바뀌므로 S1은 건드리지 않았다.
2. **병합 항목은 인자만으로 재실행되지 않는다**(상대 파일이 필요). 상태는 역효과를 접어 만들므로 복구·재오픈은 영향이 없다. 감사나 서버 동기화에 자기완결이 필요하면 델타를 따로 저장해야 한다. 앞선 병합 기준도 상대 파일 없이 로그의 지문으로만 찾는다.
3. **검사 규칙이 커맨드 규칙과 중복된다**(문이 벽 안, 레벨 이름 유일, 이제 입력 검사도). 불변식을 한 곳에 선언해 커맨드와 병합이 공유해야 한다. 지금은 시험이 상수·규칙의 일치를 대조한다.
4. **필드 단위의 한계**: 같은 벽을 양쪽이 `wall.move`하면 축선이 같은 필드라 충돌이다. 연산 의도를 보존하려면 델타형 필드나 커맨드 수준 변환이 필요하다(미시험).

## 한계 / 미확인

- 범위는 S1 모델뿐이다. 패밀리·뷰·시트·주석 정의는 단위로 확장해야 한다. 규칙과 시나리오는 저자가 정했으므로 실제 협업 패턴의 대표성은 미확인이다.
- 2자 병합만 다룬다. N자·교차(criss-cross)·서버 순서화·실시간 동시 편집은 범위 밖이다. 앞선 병합 기준은 교차 병합에서 어느 쪽도 후손이 아니면 공통 접두로 되돌아가 거짓 충돌이 남을 수 있다(조용한 덮어쓰기는 아니다).
- 규모 미측정: 최대 시험은 벽 300개, 충돌 300건이다. 5,000요소 병합 시간·메모리는 재지 않았다(겹친 벽 1200개는 위반 판정만 측정). 상대 로그 전체와 접두 지문을 매번 읽고 해시하므로 로그가 아주 길면 병합 시간이 로그 길이에 비례한다.
- 사이드카 정리는 상대가 비정상 종료한 WAL만 남은 드문 경우 "우리가 만든 것만 지운다"에 기대고, 그 사이 다른 프로세스가 같은 파일을 열었으면 POSIX에서는 지워질 수 있다(Windows는 열린 파일이라 실패하고 넘어간다). 시험은 Windows에서만 했다.
- 상대 로그 검증은 S1 모델의 모양(레벨·벽·문, 관계 3종)을 코드에 박았다. 모델이 넓어지면 같이 고쳐야 한다.
- 사람이 손으로 고친 상대 파일의 모든 변조를 막는다고 주장하지 않는다. 막는 것은 위 검사가 보는 모양·값·구조 위반이다.
- 충돌 보고가 실무자에게 이해되는지, 해결 UI 흐름은 **미확인(사람 판정 필요)**.
- Windows 한 대, Python 3.12에서만 시험했다.
