# 로드맵

기준일 2026-11-07. 인월(PM)은 **전업 1인 + AI 에이전트의 추정치**이며 근거는 5절에 있다. 기간은 주당 40시간 기준이다. 주 20시간이면 두 배로 잡는다.

## 1. 순서 원칙

위험이 크고 되돌리기 어려운 것부터 검증한다. 각 스파이크는 버릴 코드로 작성한다. 관문(G)에서 계속할지 정한다.

```text
S0 기준선 ─ G0 ─ S1 코어·레지스트리 ─ S11 양쪽 클라이언트 ─ S2 왕복 ─ S3 증분 도면 ─ S10 헤드리스 ─ G1
                                                                                      │
              S4 패밀리 · S5 연관 주석 · S6 뷰어 · S7 패키징 · S8 병합 · S9 납품 규칙
                                                                                      │
                                     G2 ─ 1단계 ─ 2a 헤드리스 저작 ─ G3 ─ 2b GUI ─ 3단계 이후
```

스파이크 합계 약 15주(3~4PM). S11을 앞당긴 이유는 제어 경로가 이후 모든 스파이크의 시험 수단이기 때문이다.

**확정 제약(ADR-0011)**은 모든 단계의 합격 기준에 들어간다.

- **패리티 G**: GUI 전용 기능 0개. 제외 목록은 `gui_exempt.yaml`뿐이다.
- **패리티 C**: 레지스트리의 모든 커맨드가 CLI와 MCP에서 같은 결과를 낸다.
- **패리티 A**: 모든 기능이 Claude와 Codex 양쪽에서 호출된다.
- **헤드리스 H**: GUI 패키지 없는 CI에서 무인 완주한다.

## 3. 첫 스파이크 S0: 바로 착수용 작업 지시

### 목적

Bonsai, FreeCAD, BimCraft, ConstructCAD, ifc-lite로 **같은 건물을 같은 기준**으로 시험해 G0 판단 자료를 만든다. 지금까지의 판정은 대부분 README와 커뮤니티 근거다.

### 착수 승인과 남은 결정

- S0 착수는 사용자가 승인했다(2026-11-07, D0). `spikes/` 폴더, venv·패키지, 후보 도구(FreeCAD, ConstructCAD, BimCraft, Bonsai 애드온 등) 설치가 범위다.

### 환경

```powershell
# 3.14는 쓰지 않는다
cd spikes/s0-baseline
py -V:3.12 -m venv .venv
.venv\Scripts\python -m pip install ifcopenshell==0.9.0.post1 ifctester
```

- Bonsai: IfcOpenShell 릴리스의 `bonsai_py311-...-windows-x64.zip`을 설치된 Blender 4.5에 넣는다. Python 버전 대응은 설치 시 확인한다.

- 제어 시험 추가 도구: `ifcedit`, `ifcopenshell-mcp`, `freecad-mcp`, `ccad`(ConstructCAD 설치본 포함), `@ifc-lite/mcp`.

## 3-1. S11 작업 지시: 양쪽 클라이언트 종단 시험

### 대상

| 클라이언트 | 시험 방법 |
|---|---|
| Claude Code CLI | `claude -p --output-format stream-json --mcp-config <파일> --allowedTools <목록>` |
| Codex CLI | `codex exec --json --skip-git-repo-check` + 임시 `CODEX_HOME` 설정 |
| Claude 데스크톱 앱 | 같은 등록으로 수동 시나리오 1회, 대화 기록 보관 |
| Codex 데스크톱 앱 | 같은 등록으로 수동 시나리오 1회, 대화 기록 보관 |

버전은 "이 PC 현재 버전"과 "최신판" 둘로 시험한다. PATH 기준 현재 `claude` 2.1.162, `codex` 0.147.0이다. 비대화 플래그의 정확한 조합은 착수 시 각 도움말로 확인한다.

### 시험 3층

| 층 | 방법 | 범위 | 빈도 |
|---|---|---|---|
| A. 프로토콜 | 공식 SDK 클라이언트로 stdio 서버 호출 | **모든 커맨드**를 `examples` 입력으로 CLI·MCP 실행, 결과 비교 | 커밋마다 |
| B. RA-01 시나리오 | 실제 클라이언트에 같은 프롬프트 | 커맨드 그룹 전부, 메타 도구 8개 전부, 위험 등급 전부 | 야간 |
| C. 전수 호출 | 실제 클라이언트가 전체 커맨드 목록을 묶음별로 실행 | **모든 커맨드** | 릴리스마다 |

메타 도구 구조에서는 커맨드가 같은 경로를 타므로 B가 클라이언트 위험 대부분을 잡는다. 그래도 C를 합격 기준으로 둔다. 요구가 "모든 기능"이기 때문이다. 토큰 비용은 S11에서 측정해 보고한다.

### RA-01 시나리오

프롬프트는 사양 표(3절)와 작업 목록만 주고 커맨드 이름은 주지 않는다.

1. 빈 프로젝트를 만들고 RA-01을 모델링한다.
2. 평면 2장, 단면 1장, 입면 4장, 문·창 일람표, A1 시트 2장을 만든다.
3. `render.sheet`로 시트 이미지를 받아 눈으로 확인한다.
4. E1(벽 이동)을 **dry-run 후 실행**한다. 도면과 일람표 값을 다시 확인한다.
5. E2, E3을 적용하고 한 번 되돌렸다가 다시 적용한다.
6. IDS 검사를 돌리고 위반을 고친다.
7. 시트 PDF, DXF, IFC를 내보내고 M1~M9를 검사한다.
8. 파괴적 커맨드(기존 PDF 덮어쓰기)를 확인 토큰 절차로 실행한다.
9. 작업 폴더 밖으로 쓰기를 시도해 `PATH_DENIED`를 확인한다.
10. 오래 걸리는 작업을 `job`으로 추적한다.

### 추정 방식과 한계

- 모듈별로 쌓아 올린 상향식 추정이다. COCOMO 같은 공식은 AI 보조 환경에서 근거가 약해 쓰지 않았다.
- 상한과 하한의 차이는 코드 작성이 아니라 **검증 부담**에서 나온다. 골든 테스트로 자동화되는 부분은 하한, 도면 품질처럼 사람이 봐야 하는 부분은 상한에 가깝다.
- AI 없이 같은 범위를 하면 2~3배가 든다고 가정했다(추정, 측정 없음).
- 이 숫자는 설계자의 판단이다. S0~S3이 끝나면 실측으로 다시 쓴다.
- 2026-11-14 G2에서 위 세부표를 스파이크 실측으로 다시 썼다(아래 "재추정" 열, 근거는 [g2-gate.md](g2-gate.md) 4절). 원래 수치는 "2026-11-07 추정" 열에 그대로 남겼다. 스파이크 실적은 달력 4일이지만 사용자 감독 시간을 재지 않아 인월로 환산하지 못했다.
