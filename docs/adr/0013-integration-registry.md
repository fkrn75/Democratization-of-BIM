# ADR-0013: 스파이크 통합 — 종류 레지스트리, 시작 상태 기록, 저작 확인 단일 관문

- 상태: 제안 (G1 선행 리팩터링, 브랜치 `spike/integration`)
- 근거: `docs/integration-g1.md`(의미 충돌 6건), `spikes/integration/report.md`
- 관련: ADR-0005(정본 분담), ADR-0006(의존성 그래프), ADR-0008(패밀리)

## 문제

스파이크 S2(외래 IFC), S3(도면), S4(패밀리), S5(주석), S8(병합)은 각자 같은 코어를 고쳤다. 텍스트로는 15~17덩어리만 충돌했지만, 합치면 git이 잡지 못하는 의미 충돌 6건이 생겼다. 원인은 둘이다.

1. **"무엇이 있는가"의 목록이 모듈마다 따로 있었다.** 요소 종류(엔진의 투영 순서, IFC 클래스 표, 병합의 화이트리스트, 가져오기의 분류표, 질의의 비 IFC 집합), 관계 종류(병합의 `REL_KINDS`, 삭제 루프, `element.get` 의 읽기 목록), 효과 태그(`invert_effect`, `input_keys_of`, `_apply_effect`). 종류를 하나 더하면 목록을 전부 고쳐야 하는데 하나라도 빠지면 합친 뒤에만 드러났다.
2. **"어떤 상태가 정본인가"가 두 곳이었다.** S2는 가져온 시작 상태를 테이블에만 풀어 두었고(로그 밖), S8은 로그만 접어서 상태를 안다. 저작 확인(`ctx.authored`)은 커맨드가 각자 불러야 했고 부르지 않으면 통과했다.

## 결정

1. **`dobim_core/kinds.py` 가 요소 종류·관계 종류·효과 태그의 정본이다.** ifcopenshell 을 import 하지 않는다. 엔진(`invert`, `input_keys_of`, `_apply_effect`, 투영 순서), IFC 모델(고정 IFC 클래스), 질의(`NON_IFC_KINDS`, `bucket_of`), 병합(행·효과 검사, 생성/삭제 순서, 관계 종류별 위반 이름), 가져오기(분류표), 커맨드(읽기·삭제 관계 목록, `element.query` 종류)가 이 표에서 파생한다.
   - 효과 태그의 "그래프 입력 키"는 한 함수(`EFFECTS[태그].keys`)이고 `input_keys_of` 와 `_apply_effect` 가 같은 것을 쓴다. `att`(외래 부속 스냅숏)는 파생값의 입력이 아니라 키가 없다.
2. **가져온 시작 상태는 로그 seq 0 항목(`ifc.import`)으로도 기록한다.** 요소 생성·관계 맺기 효과이며 리비전(rev)에 세지 않고 되돌리기 스택에 들어가지 않는다. 같은 파일을 가져온 복사본끼리는 이 항목이 같아 공통 조상이 된다. 병합은 이 항목부터 접는다. 가져온 IFC 가 원래 갖고 있던 속성·재료(로그에 없는 값)를 한쪽이 바꾸거나 지웠으면, 그 이전 값을 조상에 시드로 넣어 삭제가 사라지지 않게 한다.
3. **저작 확인은 효과를 내보내는 쓰기 관문(`Ctx.put_el`, `Ctx.rel`, `Ctx.set_material`)에서 한 번 더 한다.** `ctx.authored()` 는 좋은 오류 메시지를 위한 앞단이고, 빠뜨린 커맨드(`wall.split`, `family.place`, 주석 대상)나 병합의 요소 쓰기도 동결된 요소를 바꾸지 못한다(`ELEMENT_FROZEN`). 관계는 맺을 때만 검사한다(저작 문을 지울 때 분리된 호스트와의 관계도 끊어야 한다).
4. **해시 형식에 번호를 둔다(`CLOSURE_FORMAT`).** `make_norm`(요소 클로저와 의미 덤프가 같이 쓰는 정규화)이 바뀌면 번호를 올린다. 열 때 번호가 다르면 가져온 프로젝트를 원본 바이트로 다시 판정해 `element.projection_hash` 를 갱신한다(저작 → 분리로 바뀐 요소는 동결하고 시작 상태 기록도 고친다. 분리 → 저작으로는 되살리지 않는다).
5. **도면은 저작 벽만 그리고 생략한 개수를 알린다.** 외래 요소는 형상 정보가 없고 분리된 벽의 의도 값은 낡았다. 호스팅된 요소의 개구부는 문(`sill`)과 패밀리 인스턴스(`cut`)를 따로 계산한다.

## 결과

- 의미 충돌 6건과 보강 시험 2건을 `spikes/s1-core/tests/test_integration_g1.py` 가 고정한다.
- 종류를 더하려면 `kinds.py` 한 곳을 고치고, `DELETE_REL_NAMES` 와의 일치 검사가 import 때 빠진 곳을 알린다.
- import-linter 계약이 병합·종류 레지스트리·패밀리 순수 모듈의 ifcopenshell 직접 사용을 감시한다. 허용: engine, ifc_model, foreign(외래 IFC 를 읽는 가져오기 계획), family.ifcproj(패밀리의 IFC 투영), family.validate(IFC4 스키마의 클래스 이름 확인).

## 알려진 한계

- 통합 전에 가져온 프로젝트(스파이크 형식)에는 시작 상태 기록이 없다. 병합하려면 `ifc.import` 로 다시 가져와야 한다(병합이 `CONSTRAINT` 로 알린다).
- ~~패밀리·뷰·주석은 가져오기에서 의도를 복원하지 않고 외래로 분류된다.~~ 패밀리 타입·인스턴스는 ADR-0014 로 복원한다. 뷰·치수·태그는 ADR-0015 로 복원한다(프로젝트 속성셋 `DoBIM_Defs`).
- 병합의 패밀리 인스턴스 규칙은 호스트 벽 안에 개구부가 들어가는지와 평가 오류만 본다(레시피 제약 전체를 병합 쪽에서 다시 구현하지 않고 `queries.ifc_spec` 평가를 쓴다).
