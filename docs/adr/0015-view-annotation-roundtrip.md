# ADR-0015: 뷰·치수·태그 정의의 IFC 왕복 — 프로젝트 속성셋에 싣고 가져올 때 검증해 되살린다

- 상태: 제안 (ADR-0014 의 후속, 브랜치 `spike/integration`)
- 근거: `spikes/integration/report.md` 11절, `spikes/s1-core/tests/test_integration_views_rt.py`
- 관련: ADR-0005(정본 분담, 외래 IFC 분류), ADR-0012(주석 참조), ADR-0013(통합 레지스트리), ADR-0014(패밀리 왕복, 이 문서가 그 한계 절을 닫는다)

## 문제

뷰(S3: `view.create` 등)와 치수·태그(S5: `annot.*`)는 IFC 신원이 없는 의도 요소다(`kinds.NON_IFC_KINDS`: 도면은 항상 의도에서 파생하는 그림이다). 그래서 내보낸 IFC 에는 이름도 id 도 `IfcAnnotation` 도 없고, 저작 프로젝트를 내보냈다 다시 가져오면 뷰·치수·태그가 사라졌다(ADR-0014 의 알려진 한계, 통합 보고서 10.4절).

## 후보

| | (a) 정의마다 `IfcAnnotation` + `DoBIM_Intent` | (b) 프로젝트 속성셋 한 속성에 정의 묶음 | (c) **프로젝트 속성셋, 정의마다 속성 하나(채택)** |
|---|---|---|---|
| 다른 도구가 읽을 때 | `IfcProduct` 가 늘어 모델 트리에 형상 없는 개체가 뜨고, `IfcAnnotation` 은 2D/3D 주석 형상을 담는 클래스라 뷰(모델 요소가 아니다)를 담기엔 뜻이 다르다. 형상이 없는 주석을 가진 도구는 경고하거나 버릴 수 있다 | 모르는 속성셋이라 무시한다 | 같다(모르는 속성셋은 무시) |
| 기존 판정 체계(요소 단위 클로저) | 클로저는 형상·배치·관계를 본다. 뷰·치수·태그에는 클로저에 넣을 형상이 없어(그림은 파생) 판정 규칙을 새로 만들어야 하고, `IfcProduct` 수가 바뀌어 `ifcdiff`·M1~M8 지표·`CLOSURE_FORMAT`(요소 클로저 구성) 전부에 닿는다 | 클로저 체계에 닿지 않는다 | 같다 |
| id 안정성 | 요소 id 가 곧 `GlobalId`(22자)다. 안정 | 정의 안의 id 문자열. 안정 | 속성 이름 = 요소 id, 정의 안의 참조 = 요소 id. 안정 |
| 부분 소유·보존 | 요소 단위(좋다) | 한 속성이라 하나가 손상되면 전체를 못 믿는다. 하나를 고치려면 전체를 다시 쓴다 | 정의 하나가 속성 하나: 손상된 것만 건너뛰고, 건너뛴 속성은 그대로 남기며, 바뀐 것만 쓴다 |
| 변조 탐지 | 위치(배치)를 클로저로 비교할 수 있다. 그러나 그 위치는 의도에 이미 있는 값의 복제일 뿐 | 값에 해시를 넣어야 한다 | 같다 |
| 규모 | 요소 수만큼 엔티티·관계(만 단위에서 무겁다) | 전체 크기 상한이 한 속성에 걸린다 | 정의 하나당 상한(16KB), 개수 상한 |

(a)를 택하지 않은 가장 큰 이유는 두 가지다. ① 뷰는 모델 요소가 아니므로 `IfcProduct` 로 올리면 IFC 의 의미를 바꾼다(다른 도구에서 비어 있는 주석 개체가 생긴다). ② 요소 클로저로 변조를 가릴 수 없는 이유(그림이 파생이라 IFC 에 비교할 형상이 없다)는 (a)에서도 그대로여서, 어차피 정의 자체에 변조 탐지가 필요하다. 그러면 정의를 싣는 그릇은 가장 작게 닿는 쪽(프로젝트 속성셋)이 낫다.

## 결정

1. **그릇: `IfcProject` 의 속성셋 `DoBIM_Defs`, 속성 하나 = 정의 하나.** 속성 이름은 요소 id(22자 GlobalId 형식), 값은 `IfcText` JSON `{"kind", "family_id", "params", "check"}` 다. `params` 는 의도 저장소의 행 그대로이고(값이 항상 파생인 치수·태그의 `home`·`dirs` 같은 저장 값 포함), `check` 는 `sha256(canon({id, kind, params}))` 다. id 를 해시에 넣어 다른 id 밑으로 옮겨 붙인 정의를 거른다. 정의가 하나도 없으면 속성셋도 만들지 않는다: **뷰·주석이 없는 프로젝트의 IFC 는 바이트까지 그대로다**(마지막 정의를 지우면 속성셋도 지운다).

2. **파일의 정의는 믿지 않는다 — `viewdefs.parse_def`(순수 모듈).** 크기 상한(정의 16KB, 개수 100,000)·NaN/Infinity·거대 정수·깊은 중첩 거절 → 키 집합 → 종류·`family_id` → 파라미터 모양(`kinds.row_params_error`: 병합이 로그를 거르는 것과 같은 검사) → 값 범위·타입(커맨드가 만들 수 있는 것만: 뷰 좌표 ±1e7, 간격 ±1e5, 저장 위치 ±1e9, 축척 정수 1~1000, 절단선 1mm 이상, 높이 치수만 `at`, 참조 문법과 역할) → 짝 없는 서로게이트 거절 → `check` 일치. 하나라도 어긋나면 그 정의만 복원하지 않는다(오류로 죽지 않고 경고 한 줄).

3. **`check` 는 변조 탐지이고 인증이 아니다.** 외부 도구가 값 일부만 고치면(위치·참조·뷰 설정) 해시가 어긋나 복원하지 않는다. 정의 전체를 맞는 해시와 함께 다시 쓰는 쪽은 막지 못한다. 그런 정의도 2 의 모든 검증과 4 의 참조 검사를 통과해야만 복원되고, 복원된 뒤에는 커맨드로 만든 것과 같다(최악의 피해 = 잘못된 도면 한 장, 요소 형상은 건드릴 수 없다).

4. **참조 무결성(파일 안의 요소 판정이 끝난 뒤 판단).**

   | 정의가 가리키는 것 | 파일 안의 상태 | 동작 |
   |---|---|---|
   | 평면 뷰의 레벨 | 저작 레벨 | 복원 |
   | | 없음 | 복원(고아 뷰). 저작 상태에서 레벨을 지운 뒤와 같고 `model.validate` 가 오류로 알린다 |
   | | 분리·외래·다른 종류 | **복원하지 않음**(분리 레벨의 고도는 낡은 값이다) |
   | 치수·태그의 뷰 | 복원된 뷰 | 복원(뷰가 평면·단면·입면인지가 치수 종류와 맞아야 한다) |
   | | 없거나 복원되지 않음 | 복원하지 않음 |
   | 치수 참조 `a`/`b`, 태그 대상 | 저작 벽·문·레벨(종류 일치) | 복원 |
   | | 파일에 없음 | 복원(고아 주석: `target_deleted`). 저작 상태에서 대상을 지운 뒤와 같다 |
   | | 분리·외래·종류 불일치, **같은 파일의 다른 정의 id(뷰·치수·태그, 자기 자신 포함)** | **복원하지 않음**(낡은 값을 재게 된다. `ctx.authored` 가 생성 때 막는 것과 같은 규칙). 정의 id 는 "있지만 요소 종류가 아님"이지 "파일에 없음(고아)"이 아니다 |
   | 정의 id | 요소·타입·뼈대·프로젝트의 GlobalId 와 겹침, 같은 이름의 속성이 둘, 같은 이름의 뷰가 둘 | 겹친 정의를 복원하지 않음(오류 아님) |
   | 속성셋 | `DoBIM_Defs` 가 둘 이상 / 프로젝트가 하나가 아님 | 어느 것도 읽지 않음(모호) |
   | 길이 단위 | 밀리미터가 아님 | 읽지 않음(요소 의도와 같은 이유) |

   참조 대상의 종류 기대는 종류 레지스트리 `kinds.ElementKind.ref_kinds`(뷰의 `level`, 태그의 `view`·`target`, 치수의 `view`)와 `kinds.ref_kind_error` 한 곳에 있고, 가져오기가 그 표로 검사한다(치수의 `a`/`b` 는 참조 문자열의 종류 접두사가 기대 종류다). 예전 프로젝트에 이미 종류가 어긋난 참조가 저장돼 있어도 도면·치수 해석은 그 참조를 고아로 풀어 터지지 않는다(`annot.dim_flags`·`drawing.view_cfg` 방어).

   복원하지 않은 정의의 속성은 **파일에 그대로 남고, 내보낼 때도 건드리지 않는다**: 이 프로젝트가 소유하는 것은 복원한 정의 id 와 그 뒤에 새로 만든 정의 id 뿐이다(시작 상태 기록 seq 0 에 정의로 들어 있던 id 가 소유 목록이다). 가져온 뒤 지운 정의는 내보낼 때 속성도 지운다.

5. **정의 행은 가져온 프로젝트에서 평범한 의도 요소다.** `origin = authored`, `ifc_class = ""`, `family_id` 는 커맨드가 만드는 값(`view.basic`·`annot.dim`·`annot.tag`), 치수·태그는 관계 `annot_of`(→ 뷰)를 가진다. 시작 상태 기록에 들어가므로 병합·되돌리기·재생이 그대로 쓴다. 투영 클로저가 없어 `detached` 가 아니라 복원/건너뜀만 있다.

6. **엔진.** `flush_ifc` 끝에서 정의를 속성셋에 맞춘다(`Engine._flush_defs`). 행은 불변이라 같은 객체면 텍스트를 다시 만들지 않고, 바뀐 정의의 속성만 쓴다. 프로젝트 속성셋과 관계의 `GlobalId` 는 프로젝트 UUID 에서 파생한다(무작위면 세션마다 `ifcdiff` 가 바뀐 것으로 센다). IFC 쪽 갱신이 실패하면 속성처럼 오염으로 표시하고 로그에서 다시 만든다.

7. **형식 번호.** `CLOSURE_FORMAT` 는 올리지 않는다: 요소 클로저(제품·타입)와 의미 덤프의 정규화는 그대로이고, 새로 생기는 것은 프로젝트 속성셋과 그 관계뿐이다(의미 덤프의 기존 항목에 새 규칙이 적용되지 않는다). 의도에는 별도 형식 번호가 없고 모양을 키 집합으로 엄격히 검사한다(ADR-0014 와 같다). `.dobim` 파일의 스키마도 그대로다: 정의는 항상 의도 행에서 파생하므로, 이 변경 전에 만든 프로젝트는 열어서 내보내기만 하면 정의가 실린다. 이 변경 전에 내보낸 IFC(속성셋 없음)를 가져오면 뷰·주석 없이 열린다(이전과 같다). 이 변경 전에 가져온 프로젝트는 열 때 다시 판정하지 않는다.

8. **복원하지 않은 정의와 같은 id 로 뷰·치수·태그를 만들면: 거절하지 않고 덮어쓰되 경고하고, 그 정의가 사라지면 원본을 되돌린다.** 후보 (a) 소유하지 않은 정의 id 로 생성 거절(ID 충돌), (b) 덮어쓰기 허용 + 경고 + 되돌리기로 외부 정의 복원 중 (b)를 골랐다. 이유: (a)는 커맨드가 파일 안의 정보(소유하지 않은 속성)를 알아야 하는데 커맨드는 의도 상태의 순수 함수이고(import-linter 로 ifcopenshell 금지), 그 정보를 상태에 넣으면 병합·재생에서 복사본마다 달라진다. (b)는 `IfcModel` 이 가져온 파일의 소유하지 않은 정의 속성의 원본(`_ext_defs`)을 기억해 두고, 새 정의가 그 속성을 덮어쓴 뒤 정의가 사라지면(지우기·되돌리기) 지우지 않고 원본으로 복원한다. 그래서 속성의 최종 값은 "그 id 의 정의가 상태에 있으면 그 정의, 없으면 파일의 외부 원본"이라는 상태의 함수이고, 생성·삭제·되돌리기·다시하기·재오픈 어떤 경로로 가도 같다. 생성 때 `ctx.external_def` 가 `view.create`·`annot.dim.create`·`annot.tag.create` 의 id 가 외부 정의와 겹치면 경고를 낸다. 값이 문자열이 아닌 외부 속성(`IfcReal` 등)도 타입까지 되돌린다. 같은 이름 속성이 둘인 외부 정의는 어느 쪽이 원본인지 몰라 되돌리지 않는다.

## 결과

- 뷰·치수·태그(와 패밀리 문)가 있는 저작 프로젝트를 내보냈다 다시 가져오면 전부 복원되고 `authored` 이며 해시 3종이 같다. 두 번 내보낸 IFC 는 바이트까지 같고 `ifcdiff` 0(strict 포함). 복원된 뷰의 도면 산출(`view.linework`, SVG 내보내기)이 원본과 같다.
- 왕복 뒤 같은 편집열(뷰·주석 생성·수정·삭제, 참조 요소 삭제, 되돌리기·다시하기, 병합)이 저작 프로젝트와 같은 해시를 낸다.
- 뷰·주석이 없는 프로젝트의 IFC·해시는 바뀌지 않는다(패리티 픽스처 해시 불변).

## 알려진 한계

- `check` 는 인증이 아니다(결정 3). 정의 전체를 올바른 해시로 다시 쓴 위조는 되살려진다. 예: 치수의 참조를 다른 저작 벽으로 바꿔 해시까지 맞추면 그 벽을 재는 치수로 복원된다.
- 복원하지 않은 정의의 id 와 같은 id 로 사용자가 뷰를 새로 만들면 그 속성을 덮어쓴다(결정 8: 경고하고, 그 정의가 사라지면 원본이 돌아온다). 같은 이름의 외부 속성이 둘이었던 경우는 돌아오지 않는다.
- 프로젝트가 정확히 하나가 아닌 IFC(규격 위반)에는 정의를 싣지도 읽지도 않는다.
- 뷰·주석의 IFC 표현은 다른 BIM 도구에서 의미가 없다(보이지 않는다). 그 도구에서 도면을 보려면 정의가 아니라 도면 내보내기(SVG·PDF)를 쓴다.
- 정의가 수만 개인 파일의 가져오기·내보내기 시간은 정의 1,000개까지 쟀다(통합 보고서 11절).
