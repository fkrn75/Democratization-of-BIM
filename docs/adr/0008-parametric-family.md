# ADR-0008. 파라메트릭 패밀리: 선언형 레시피를 IFC 타입으로 투영

- 상태: **제안** (S4로 검증)
- 일자: 2026-11-07

## 맥락

IFC에는 패밀리 개념이 없다. 있는 것은 타입 객체(`IfcTypeProduct`)와 공유 형상(`RepresentationMap`)이다. 변형 규칙은 담지 못한다. Bonsai는 문·창 파라미터를 자체 Pset에 저장하고, BimCraft는 레시피 JSON을 `IfcGroup` + Pset에 넣고 타입당 `IfcXxxType` 하나를 만든다(반증 검토에서 코드 확인). 후자는 실재하는 선례이고 Apache-2.0이다. BimCraft는 수식 파라미터, box·extrude·revolve·sweep, 불리언, 중첩, MEP 커넥터를 갖췄지만 참조 평면과 치수 구속 해석기는 없다(`research/04-bimcraft-deep-dive.md`). 다른 IFC 앱에는 평범한 타입으로 보인다.

## 결정 (제안)

1. **패밀리는 텍스트 파일**(JSON, 스키마 검증)이다. 내용은 다음과 같다.
   - 파라미터(타입/인스턴스, 단위, 기본값, 범위)
   - 공식: 산술·조건만 있는 안전한 식 언어. 입출력과 임의 코드 실행 없음
   - 이름 있는 참조 평면(공식으로 위치 결정)
   - 형상 연산: 프로파일 압출, 스윕, 회전, 공극, 표시 조건
   - 축척별 평면 기호(문 열림 호 등). 3D 절단이 아닌 도면 전용 표현
   - 호스트 규칙, IFC 클래스·PredefinedType, Pset 매핑
2. **구속 해석기는 MVP에 없다.** 위치는 공식의 DAG로 결정한다. 문·창·기둥 같은 일반 요소는 이것으로 충분하다고 가정하고 S4에서 확인한다. 치수 끌기 편집 GUI와 해석기(planegcs 등 라이선스 확인 필요)는 3단계다.
3. **IFC 투영**: 인스턴스 파라미터를 뺀 값의 해시마다 `IfcDoorType` 등과 `RepresentationMap`을 하나 만든다. 인스턴스가 형상을 바꾸면 개별 표현을 둔다. 레시피 전문과 파라미터는 IFC 안에 Pset으로도 넣는다. 다른 도구에서는 평범한 문으로 보이고 우리 도구로 돌아오면 다시 파라메트릭이 된다.
4. **외래 타입**: IFC로 들어온 타입은 "동결 패밀리"로 배치·복제만 허용한다.
5. **자산**: 기본 라이브러리 30종을 직접 만든다. 텍스트 형식이므로 **에이전트가 사양에서 패밀리를 생성하고 검증기를 통과시키는 흐름**을 1급 시나리오로 둔다. 이것이 Revit 생태계 격차를 조금이라도 줄일 수 있는 유일한 가설이며 아직 검증되지 않았다.

## 하지 않는 것

- `.rfa` 읽기·쓰기. Revit의 수만 개 자산과 호환하는 일은 포기한다. 이것이 이 제품의 가장 큰 한계다.
- Python 스크립트 패밀리. 강력하지만 보안과 이식성을 잃는다. 고급 사용은 플러그인 API로 한다.

## 뒤집는 조건

S4에서 일반 패밀리 4종 중 2종 이상이 공식 DAG로 표현되지 않으면 해석기를 앞당기거나 범위를 줄인다. 레시피의 IFC 저장 크기가 납품 파일에 부담이면 해시 참조와 사이드카로 옮긴다.
