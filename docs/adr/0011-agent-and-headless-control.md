# ADR-0011. 전 기능 CLI·MCP 제어, Claude·Codex 동등 지원, 헤드리스 실행

- 일자: 2026-11-07
- 상태 구분:
  - **요구사항: 승인** (2026-11-07 사용자 지시)
  - **구현 방식: 제안** (S1, S10, S11로 검증)

## 요구사항 원문

1. "모든 기능은 mcp나 cli로 제어할수 있어야해"
2. "클로드나 코덱스에서 모든 기능을 사용할수 있어야하고"
3. "핸드리스모드도 있어야해" (헤드리스로 해석)

## 해석

| 항목 | 정의 |
|---|---|
| 지원 클라이언트 | Claude Code CLI, Claude 데스크톱 앱, Codex CLI, Codex 데스크톱 앱 |
| 동등성 | 모든 기능이 양쪽에서 같은 결과를 낸다. 한쪽 전용 기능은 두지 않는다 |
| 헤드리스 | GUI, 디스플레이, GPU 없이 코어 패키지만으로 모든 기능이 동작한다 |
| 기능 | 프로젝트 상태를 읽거나 바꾸는 것, 산출물을 만드는 것, 결과에 영향을 주는 설정 전부 |

기능 범위와 제외 목록은 `docs/architecture.md` 15.2절에 있다. 제외는 저장도 출력도 바꾸지 않는 순수 화면 조작에 한한다.

## 결정 (제안)

1. **커맨드 레지스트리 하나**에 모든 기능을 스키마와 함께 등록한다. CLI와 MCP는 여기서 생성한다. GUI도 같은 커맨드만 호출한다. 변경 커맨드는 기존 커맨드 로그(ADR-0005)에 기록한다.
2. **공통 경로는 stdio MCP + CLI**로 한다. 두 클라이언트의 공통 부분집합에 맞춘다.
3. **MCP는 고정된 소수의 메타 도구**로 노출한다. 검색 → 스키마 조회 → 실행 순서다. 위험 등급별로 실행 도구를 나눠 승인 정책이 살아 있게 한다.
4. **클라이언트 차이는 어댑터에만** 둔다. 코어에 클라이언트 분기를 두지 않는다.
5. **패키지를 분리**한다. `core`(라이브러리·CLI·MCP·CPU 렌더)는 GUI에 의존하지 않고, `app`이 `core`에 의존한다. 의존성 검사로 강제한다.
6. **3D 헤드리스 렌더의 기본은 CPU 진단 렌더**다. GPU는 있으면 쓰는 선택 경로다.
7. **코어는 Windows와 Linux x64를 1급으로 지원**한다. GUI는 Windows만 지원한다. Linux를 넣는 이유는 CI와 서버가 대체로 Linux이고 `ifcopenshell 0.9.0.post1`에 `manylinux_2_31_x86_64` 휠이 있기 때문이다(PyPI 확인).

MCP 명세 현행판은 2026-07-28이다. 프로토콜 세션 제거, 상태 없는 코어, Roots·Sampling·Logging 폐기 예정, Tasks 확장 분리가 들어갔다. 서버 측 상태는 **도구 인자로 넘기는 명시적 핸들**을 쓰라고 한다. 이 설계와 맞다.

### 이 PC의 버전 주의 [실측]

PATH의 `claude`는 2.1.162, `codex`는 0.147.0이다. 위 문서가 말하는 기능 중 일부는 더 새 버전을 요구한다(Claude 이미지 파일 저장 v2.1.283 등). 데스크톱 앱은 자체 번들 버전을 쓸 수 있다. 서버는 구버전 핸드셰이크(`initialize`)와 2026-07-28을 모두 처리해야 하고, 최소 지원 버전은 S11 결과로 정한다.

### 끝내 미확인

- Codex에서 MCP resources·prompts·elicitation의 실제 동작
- Codex에서 structuredContent를 모델이 보는 방식. 그래서 JSON을 텍스트로도 넣는다
- Codex의 이미지 크기 제한과 토큰 환산
- Codex의 기본 출력 한도 값과 도구 지연 로딩의 공식 동작
- Claude 데스크톱 앱에서 Code 탭이 아닌 일반 대화의 MCP 등록 경로와 같은 동작 여부
- Codex 샌드박스가 MCP 서버 프로세스의 파일 접근에 미치는 영향(Windows)
- Python MCP SDK(`mcp` 2.3.0, MIT)의 2026-07-28 지원 범위
- 위 항목은 S11에서 측정한다.

## 대안

| 대안 | 기각 이유 |
|---|---|
| 커맨드마다 MCP 도구 1개 | 수백 개면 목록이 컨텍스트를 차지하고, 지연 로딩이 양쪽에서 같다고 보장할 수 없다. 선택 프로필(`--tools=direct`)로만 제공 |
| CLI만 제공하고 셸로 호출 | 구조화 결과, 승인 등급, 이미지 반환을 잃는다 |
| MCP 도구 단 1개(`run`) | 읽기와 쓰기를 구분할 수 없어 승인 정책이 무력해진다 |
| GUI 우선, 나중에 API 노출 | 표면이 어긋난다. Bonsai 조작자나 BimCraft 이슈 #14가 그 사례다 |
| GPU 오프스크린만 지원 | GPU 없는 CI·서버에서 깨져 요구사항 위반 |

## 영향

- ADR-0001: 코어 우선은 선호에서 필수로 바뀌었다. Bonsai 플러그인은 요구를 온전히 충족하지 못한다. ConstructCAD가 강력한 후보가 됐다.
- ADR-0004: Python 코어는 유지하되 시작 시간, stdout 오염, 배포 형태를 S11에서 검증한다. 앱은 코어의 선택 클라이언트가 된다.
- 로드맵: 스파이크 S10, S11 추가. 저작 MVP를 "헤드리스 저작(2a)"과 "GUI(2b)"로 나눈다. 인월은 20~37에서 24~44로 증가(추정).

## 뒤집는 조건

- S11에서 메타 도구 탐색 성공률이 90% 미만이면 주요 커맨드를 직접 도구로 추가 노출한다. 그래도 모든 기능은 메타 도구로 닿아야 한다.
- Python 콜드 스타트가 Codex 기본 시작 제한(10초)을 안정적으로 넘기지 못하면 얇은 네이티브 실행기를 앞에 둔다.
- 요구사항 자체를 바꾸는 것은 사용자 결정이다.
