# ADR-0014: 가져오기의 패밀리 의도 복원 — 패밀리 인스턴스가 있는 저작 프로젝트의 IFC 왕복

- 상태: 제안 (G1 선행 리팩터링의 후속, 브랜치 `spike/integration`)
- 근거: `spikes/integration/report.md` 10절, `spikes/s1-core/tests/test_integration_family_rt.py`
- 관련: ADR-0005(정본 분담, 외래 IFC 분류), ADR-0008(패밀리), ADR-0013(통합 레지스트리, 알려진 한계 갱신)

## 문제

패밀리 인스턴스가 있는 저작 프로젝트를 IFC 로 내보냈다 다시 가져오면 호스트 벽이 `detached`(동결)가 됐다(통합 보고서 8절 항목 7).

1. 내보낸 파일의 패밀리 인스턴스(`IfcDoor`·`IfcWindow`·`IfcColumn` 등)와 타입(`IfcDoorType` 등)의 `DoBIM_Intent` 는 문·벽·레벨의 의도와 모양이 다르다. 가져오기(`foreign._parse_intent`)는 레벨·벽·문만 해석했으므로 인스턴스와 그 개구부(`IfcOpeningElement`)가 외래 요소가 됐고, 타입은 요소가 아니었다.
2. 호스트 벽의 투영 클로저에는 그 개구부(`voids`)가 들어 있다. 가져오기가 벽의 의도만으로 다시 투영한 벽에는 개구부가 없어 클로저 해시가 달라지고, 사유 "벽에 뚫린 개구부"로 호스트 벽이 분리됐다.

안전한 쪽의 판정이지만 저작 프로젝트가 왕복 뒤 호스트 벽의 형상을 고칠 수 없었다.

## 결정

1. **IFC 에 담는 방식은 바꾸지 않는다.** 패밀리 정의는 이미 `DoBIM_Intent` 에 있다. 타입(`ftype`)의 의도는 `{kind, family_id, params:{name, recipe(레시피 전문), recipe_hash, type_values}}`, 인스턴스(`finst`)는 `{kind, family_id, type, host|level, params}` 다. 타입 객체 속성에 따로 넣을 필요가 없다. 따라서 **의도 형식 버전도 `CLOSURE_FORMAT` 도 올리지 않는다**: 문·벽·레벨의 요소 클로저와 의미 덤프의 정규화는 그대로이고, 새 규칙(타입 클로저, 인스턴스의 타입 지정)은 새 종류에만 적용한다. 이 변경 전에 가져온 프로젝트는 열 때 다시 판정하지 않는다(옛 판정 그대로 열린다). 새 판정을 받으려면 내보낸 파일을 다시 가져온다.

2. **종류는 의도가 스스로 밝힌다.** 문·벽·레벨은 IFC 클래스로 종류를 정하던 대로 두고, `kind` 가 `ftype`/`finst` 인 의도는 IFC 클래스를 레시피가 정한다(인스턴스도 `IfcDoor` 일 수 있다). 요소 후보는 `IfcProduct` 에 더해 `IfcTypeObject`(타입)도 훑는다. 의도가 있는 타입만 요소(`ftype`)가 되고, 그 밖의 타입은 파일에 그대로 남는다(요소가 아니다).

3. **파일의 의도는 믿지 않는다 — `family/restore.py`(순수 모듈).** 크기 상한(160KB)·NaN/Infinity·거대 정수·깊은 중첩을 읽기 전에 거절하고, 아래를 모두 맞춰 본 뒤에야 후보로 삼는다. 하나라도 어긋나면 `ValueError` 이고 그 요소는 외래로 둔다(지금까지의 안전한 동작).
   - 모양(키 집합)과 파라미터 모양은 병합이 로그를 거르는 것과 같은 검사(`kinds.row_params_error`)다.
   - 타입: 레시피를 `evaluate.load_recipe` 로 검증하고, `recipe_hash` 가 레시피와, `family_id` 가 레시피 id 와, `type_values` 가 `resolve_values` 결과(완전한 검사 통과 사전)와 같아야 하며, 타입 평가가 성공해야 하고, 파일의 IFC 클래스가 레시피의 타입 클래스와 같아야 한다.
   - 인스턴스: 타입(후보)·호스트 벽 또는 레벨(후보)이 있고, 패밀리 id 가 타입과 같고, 호스팅 여부가 레시피·배치 필드와 같고, 값이 완전한 검사 통과 사전이고, 평가가 성공하고(S4 의 평가 오류·cut·elevation 규칙을 그대로 쓴다), `width`/`height` 같은 파생값이 평가한 cut 과 같아야 한다(`family.spec.inst_params` 로 `family.place` 가 저장하는 행을 다시 만들어 대조한다). 위치 계열 숫자는 ±1e9 안이어야 한다(벽·문 의도와 같다).
   - 평가는 결정적이다: 순수 함수이고 식 평가 예산(`EVAL_BUDGET`)이 폭주를 막는다. 결과는 `(레시피 해시, 값, 호스트 문맥)` 키로 캐시한다.

4. **요소 클로저에 패밀리를 넣는다.** 후보의 의도를 새 모델에 다시 투영해(`ifc_spec` 그대로) 들어온 요소와 클로저 해시를 대조하는 흐름은 같다.
   - 타입 클로저는 이름·속성·표현 지도(형상)다. 타입에 붙은 속성셋(`HasPropertySets`, `DoBIM_Intent` 포함)은 IFC 가 정본이라 뺀다. 타입은 배치가 없다.
   - 인스턴스 클로저는 기존 항목(속성·배치·표현·공간 소속·개구부 관계)에 **타입 지정**(`IfcRelDefinesByType` 의 타입 GlobalId)을 더한다. 문·벽·레벨에는 더하지 않는다(외부 도구가 타입을 붙여도 형상이 아니다).
   - 호스트 벽의 `voids` 는 기존 규칙 그대로 "개구부를 누가 채우는가"를 본다. 인스턴스가 후보면 의도 재투영에도 같은 충전자가 있어 벽은 저작으로 남는다.
   - 의도를 투영할 수 없는 후보(레시피가 그 IFC 클래스에 쓸 수 없는 속성을 요구하는 등)는 가져오기를 죽이지 않고 `detached`("의도를 투영할 수 없다")로 둔다.

5. **분리는 그 요소와 영향받는 요소만.**

   | 변조 | 결과 |
   |---|---|
   | 인스턴스를 옮김·개구부를 옮기거나 모양을 바꿈·타입 지정 관계를 지움 | 그 인스턴스만 `detached`(개구부는 외래 행). 호스트 벽은 저작 |
   | 타입의 형상·이름·속성을 바꿈 | 그 타입 `detached`, **그 타입의 인스턴스도 함께 `detached`**("패밀리 타입이 분리됨": 타입이 낡은 정의라 인스턴스를 다시 투영하면 변조된 표현 지도를 가리킨다) |
   | 호스트 벽을 옮김 | 호스트 벽만 `detached`. 인스턴스는 벽을 따라간다(문과 같다) |
   | 인스턴스만 지움(개구부 남음) | 호스트 벽 `detached`("벽에 뚫린 개구부"), 개구부는 외래 |
   | 인스턴스와 개구부를 함께 지움 | 변화 없음(요소가 사라질 뿐) |
   | 의도를 못 읽음·일관되지 않음 | 인스턴스·개구부는 외래, 호스트 벽 `detached`(지금까지와 같다) |

6. **IFC 모델이 가져온 패밀리 상태를 이어받는다(`ifc_model.py`).** 이어받지 않으면 첫 재투영이 중복을 만든다.
   - 타입 객체는 제품 색인과 따로 둔다(`_types_by_gid`): 제품 색인은 `prune` 이 요소가 아닌 제품을 지우는 데 쓰므로, 요소가 아닌 외래 타입이 지워지지 않게 한다. 시작 상태 기록(seq 0)의 `ftype` 중 지금 요소가 아닌 것만 가지치기한다.
   - 인스턴스의 타입 지정 관계(`typerels`/`type_of`), 타입의 표현 지도 유무, 인스턴스의 개구부(`openings`/`_opening_gid`)를 파일에서 이어받는다. 평면 기호 문맥(`Plan`/`FootPrint`)은 파일에 있으면 쓴다.
   - 패밀리 개구부의 GlobalId 는 이미 정해진 값(가져온 파일, 지우기를 되돌린 값)을 유지한다. 없을 때만 프로젝트 UUID 에서 파생한다(문의 `opening_guid` 와 같은 원칙).
   - 타입 지정 관계(`IfcRelDefinesByType`)의 GlobalId 는 타입 id 에서 결정적으로 파생한다. 무작위면 같은 프로젝트를 다른 세션에서 내보낼 때마다 `ifcdiff` 가 이 관계를 바뀐 것으로 센다. 의미 해시는 관계의 GlobalId 를 빼므로 해시는 그대로다.
   - 외래 부속 스냅숏(`capture_attachments`)은 타입 객체를 안다(타입은 몸체 표현이 없다).

7. **가져온 프로젝트의 타입 id.** 타입 id 는 `family.place`/`family.register` 가 레시피 해시와 타입 값에서 프로젝트 UUID 로 파생한다. 가져온 프로젝트는 UUID 가 다르므로 `family=` 로 배치하면 같은 내용의 타입이 하나 더 생긴다. 가져온 프로젝트(`has_base`)에서 파생 id 의 타입이 없고 같은 내용의 기존 타입이 있으면 그것을 쓴다(id 가 가장 작은 것). 가져오지 않은 프로젝트의 동작은 그대로다.

## 결과

- 수정하지 않은 저작 프로젝트(패밀리 포함)의 왕복은 전부 `authored` 이고 해시 3종(state·derived·ifc)이 같다. 두 번 내보낸 IFC 는 바이트까지 같다.
- 왕복 뒤 같은 편집(패밀리 수정·배치·호스트 벽 치수 변경·분할, 삭제, 되돌리기·다시하기, 타입 삭제 후 재오픈)은 저작 프로젝트와 해시 3종이 같다(프로젝트 UUID 가 같을 때. 다르면 UUID 에서 파생하는 새 요소의 id·GlobalId 만 다르다).
- 병합: 가져온 시작 상태 기록에 `ftype`/`finst` 행이 들어가며 병합은 이를 `kinds` 의 파라미터 검사로 거른다. 코어의 다른 부분은 바뀌지 않는다.

## 알려진 한계

- 뷰·치수·태그(S3·S5)는 IFC 신원이 없는 의도 요소라 IFC 만으로는 복원할 수 없다(IFC 에 담기지 않는다). 왕복하면 사라진다. 복원하려면 뷰·주석 정의를 IFC 에 싣는 형식(예: 프로젝트 수준 속성셋 또는 `IfcAnnotation`)을 정해야 하며, 이번에 하지 않았다.
- 타입 의도의 `type_values` 만 바꾸고 형상은 그대로인 변조는 타입 분리 + 인스턴스 외래(+호스트 벽 분리)로 떨어진다. 외래로 읽히는 인스턴스는 파생값이 타입 값과 어긋나 평가와 대조할 수 없기 때문이다. 안전한 쪽이다.
- 분리된 타입의 인스턴스는 형상이 그대로여도 함께 분리된다.
- 이 변경 전에 가져온 프로젝트의 패밀리 인스턴스는 외래로 남는다(열 때 다시 판정하지 않는다). 다시 가져와야 풀린다.
- 평가 비용 상한은 요소마다의 예산과 의도 크기 상한뿐이다. 후보 수가 아주 많은 파일(수만 인스턴스)에 대한 가져오기 시간은 재지 않았다.
